# ADR-0004: Fallback Strategy for Bot-Protected Static Fetching

- **Status:** Proposed (Awaiting Lead Decision)
- **Date:** 2026-11-18
- **Deciders:** Varun (Lead), AI Assistant
- **Consulted:** DAR-10, DAR-14, Risk R1

## Context and Problem Statement

DarGlobal (`darglobal.co.uk`) is protected by Imperva / Incapsula bot protection, and Wasalt (`wasalt.sa`) is protected by Cloudflare.
In accordance with DAR-14, an early test fetch of 5 DarGlobal URLs was conducted from the dev environment using `PoliteFetcher` with a standard browser User-Agent:

1. `https://darglobal.co.uk/` -> `BLOCKED` (HTTP 200, Incapsula challenge page detected)
2. `https://darglobal.co.uk/the-astera/` -> `BLOCKED` (HTTP 200, Incapsula challenge page detected)
3. `https://darglobal.co.uk/projects/` -> `BLOCKED` (HTTP 200, Incapsula challenge page detected)
4. `https://darglobal.co.uk/blog/` -> `BLOCKED` (HTTP 200, Incapsula challenge page detected)
5. `https://darglobal.co.uk/press/` -> `BLOCKED` (HTTP 200, Incapsula challenge page detected)

Wasalt (`https://wasalt.sa/en/villas-for-sale-in-riyadh`) was also probed and returned a Cloudflare challenge page (`BLOCKED`).

Because `PoliteFetcher` accurately identified the challenge signatures (markers: `visid_incap`, `/_Incapsula_Resource`, `cf_chl_prog`), none of these challenge pages were saved or indexed. However, a plain Python HTTP client (`urllib.request`) cannot retrieve content directly from either target.

This materializes **Risk R1** from Section 9 of the Project Plan.

## Decision Drivers

1. Compliance with the project plan constraint: "If they're blocked, switch to a headless browser (Playwright) and record the choice in ADR-0004."
2. Compliance with Rule 7: "If you hit something the document didn't anticipate, or a risk in section 9 materializes (e.g. DarGlobal blocks the scraper), stop and tell me — don't silently improvise a workaround."
3. Scraper politeness and rate-limiting rules must be maintained.
4. Wasalt `llms.txt` non-commercial terms and no-PII extraction requirements must remain strictly intact.

## Considered Options

### Option 1: Headless Browser with Playwright (Recommended by Plan R1)
- **Mechanism:** Run Playwright Chromium in headless (or stealth) mode to render pages and solve JavaScript challenges before extracting JSON-LD and page text.
- **Pros:** Executes client-side JavaScript challenges transparently; retrieves genuine DOM with JSON-LD.
- **Cons:** Slower than plain HTTP; requires installing Playwright + Chromium browser binaries (~150MB).

### Option 2: Cloud Unblocking / Proxy Gateway (Used in Recon)
- **Mechanism:** As noted in Recon (Section 5 of the plan), initial recon pages were fetched via Apify / proxy unblocker.
- **Pros:** High reliability, offloads rendering.
- **Cons:** External dependency; requires API key / service account.

### Option 3: Pre-rendered / Cached Sample Scrapes & Fixtures
- **Mechanism:** Fallback to seed snapshot data captured from verified sources for pipeline development while headless browser is set up.

## Proposed Decision & Next Steps
Per plan risk mitigation R1, the planned path is **Option 1 (Playwright headless scraper)**.
Per rule 7, execution is paused to notify the project lead before installing Playwright and initiating headless scraping.
